# 05 RK3568 逻辑 V28.8 · 算法说明

## 1. 总体架构

FPGA 通过千兆以太网推送 **720×1280 单通道 YRG**，RK3568 端按场景分发到五个模型，
再把决策结果编成 2 字节指令回发给 FPGA 显示。

```
FPGA ──UDP──> RK3568
               │
               ├─ 场景路由 (merged5gray 1024×1024)
               │     → 正常 / 夜间 / 导航 / 斑马线 / 行人 ...
               │
               ├─ 红绿灯分支   housing_3568 1280×768  → 灯箱框 → 判色 → 三箭头
               ├─ 车道分支     G640 640×360 灰度    → 虚线/实线 → 黄/红箭头
               ├─ 导航分支     nav6_720 1280×720    → 方向+位数 → 蓝箭头
               └─ 交警分支     cls_v2yrg3 96×96     → 单绿箭头（FPGA 靠"只一个箭头"识别）
```

**FPGA 输入固定 1280×720（16:9）**，所有模型按此尺寸训练 / 转换 / 校准。
实测与方形 1280 精度完全相同但省 44% 算力。

## 2. 模式位是「锁存」不是「按次请求」（最重要的一条）

FPGA 的模式位一旦改动，**之后所有帧**都按新模式发送，不是只影响下一帧。

历史教训：V17_5 每轮先请求灰度再请求二值，等于每轮翻两次模式，
结果二值帧无人消费、13→18 轮延迟，排空 15 ms 对 32 MB 积压远远不够。

**结论：V24 起二值通道整个删除，FPGA 只发 MODE 1（灰度 YRG），RK 端坚决不做二值化。**
这条是不可回退的硬约束，任何"临时切一下模式拿一帧二值图"的方案都会重蹈覆辙。

## 3. YRG 单通道契约

```
0 ~ 253  = 灰度
254      = 纯红
255      = 纯绿
```

- 还原成 BGR：`254 → (0,0,255)`，`255 → (0,255,0)`，其余灰度复制三通道
- 亮度灰度：`Y = (77R + 150G + 29B) >> 8` —— **77+150+29 = 256**，是精确的加权平均，不丢信息
- ⚠️ 二值图的白是 **253** 不是 255，遇到 254/255 判据时要先确认帧的形态

**每个模型的预处理各自独立，不要统一、不要质疑。** 这是队友分别指定的：
斑马线/行人直接用 `(77R+150G+29B)>>8` 灰度；导航必须用亮度灰度（红绿变换会把蓝底导航屏打成黑屏）。

## 4. 红绿灯分支：必须永远三个箭头

**捆绑硬条件**：红绿灯分支屏幕上必须同时显示左、直、右三个箭头，只是颜色不同（红/绿/灰）。

曾用"按颜色计时过期"（绿 6 轮 / 红 15 轮各自到期）实现，结果是箭头
**"从右到直再到左依次消失"** —— 已整层拆掉。无框超时一律显示全红。

判色语义（按分支互斥，同一个颜色在不同分支含义不同）：

| 分支 | 黄 | 红 | 绿 |
|---|---|---|---|
| 车道 | 可变道 | 禁止变道 | — |
| 红绿灯 | — | 停 | 行 |
| 导航 | — | — | 蓝箭头 |

## 5. 交警分支

见 `01_交警手势识别/说明/算法说明.md`。要点：

- 手势分类模型输出类别 → `CLASS_TO_KIND` → `KIND_TO_DIRECTION` 解译成通行方向
- 屏幕上**只出现一个箭头**（左转绿 / 直行红），FPGA 正是靠"只有一个箭头"判定
  交警模式并播报语音，补成三箭头会让整段演示失效
- 门槛与确认轮数按手势类别分别配置，`RELEASE_ROUNDS=1` 使手势结束立刻退出

## 6. V28.8 的调度参数（用户拍板的硬条件）

| 参数 | 值 | 说明 |
|---|---|---|
| `scene-every` | **1** | 场景模型**每轮必须跑** |
| `traffic max_hold` | **0** | 红绿灯**不许跳轮** |
| `nav max_hold` | **0** | 导航**不许跳轮** |

**⚠️ 这三个数不能改回两轮一次。** 曾经为省算力改成两轮一跑，结果是缓存的标签
被错路由，屏幕上红绿灯的三个箭头全错（V28.8 板端回归实测）。省算力请从别处省。

## 7. 已知的静默坑（上线前必读）

1. **按对象 id 缓存 = 喂上一帧给模型**
   判据：帧号在推进 + 灰度级数正常 + 推理正常，但输出恒定不变 → 先查输入串帧。
   曾经 `yrg is self._cached_yrg` 让模型永久失明（第 84 轮起检出率 0%）。

2. **分支切换必须清状态 + 回收内存**
   第一次上板暴露四件事：内核 OOM（返回 137，可用内存仅剩 150 MB）、
   车道轮亮灯、灯轮亮车道、二值帧伪造红绿灯 93 轮。
   切换要按**实际分支**判，并清空上一分支的全部状态。

3. **双重 NMS 把横排灯召回压掉一半**
   `predict()` 内部已经做过 NMS，再跑一遍 @0.45 会让召回 74.6% → 45.8%。

4. **FPGA 模式 1 和模式 2 的包头相同，分不出**
   别指望从包头判断当前是灰度还是二值。

5. **启动时 UDP OSError 会穿透导致崩溃**
   板上 5 次重启中 3 次是这个原因。`rknn.inference` 没有超时，必须用心跳看门狗。

|---|---|

| `models_runtime.py` | 五个模型的适配器（每个模型输入契约的唯一定义处） |

| `traffic_boxes.py` | 灯箱框过滤（滑动窗口集中度 + 行内高度统计） |

| `protocol.py` | 2 字节小端指令位域 |

| `model_selfcheck.py` / `check_models.py` | 启动自检（SHA256 校验） |

| `models_manifest.json` | 五个模型的尺寸 / SHA256 / 用途 |

### 模型清单（V28.8）

| 模型 | 尺寸 | 输入 | 用途 |
|---|---|---|---|
| `merged5gray_rk3568_fp16.rknn` | 8.08 MB | 1024×1024 | 场景路由（行人/斑马线/车道/红绿灯/导航） |
| `housing_3568_fp16.rknn` | 8.20 MB | 1280×768 | 红绿灯灯箱检测 v2（纯红绿域） |
| `G640_rk3568_fp16.rknn` | 3.42 MB | 640×360 | 车道灰度 |
| `nav6_720_rk3568_fp16.rknn` | 8.33 MB | 1280×720 | 导航方向 × 位数 |
| `cls_v2yrg3_rk3568_fp16.rknn` | 0.20 MB | 96×96 | 交警三分类 |

**全部 FP16，没有一份 INT8。** 理由：INT8 会把虚线类像素抹掉 87%（车道永远吐"禁止变道"）、
会把红绿掉 10~14 分、会把小框定位打散。RK3568 并非"只支持 INT8"。
