# 02 车道线二值化模型 · 算法说明

## 1. 任务定义

赛题只考**能否变道**。因此判据塌缩成：该侧边界是**白色虚线** → 可变道（黄箭头）；
否则 → 禁止变道（红箭头）。黄虚线跨过去是逆行，本就不该变道，所以"禁止跨越"的
一切（白实/黄虚/黄实/双黄/导流线）并成一类即可。

## 2. 数据

| 来源 | 说明 |
|---|---|
| A 套 | 实线/虚线实例分割，1133 张 COCO |
| B 套 | 实线/虚线语义分割，373 张含道路 |
| LaneMarking8K | 清洗后作为跨域验证（**不作为调参依据**，否则必过拟合） |
| 官方帧 | 用户手工标注的左右双标签，留出 50 帧/100 方向做评估 |

官方素材大多是路口接近画面，车道几乎不起作用；**只用一个域调参必然过拟合**，
所有几何参数都在官方 + 8K 两个域上同时看过。

## 3. 输入契约

```
BGR → FPGA 亮度灰度 Y = (77R + 150G + 29B) >> 8   （不是 OpenCV BT.601）
     → 二值化 th（训练用 th190，阈值抖动 ±18）
     → 缓存高分辨率 (1024×576) 再池化到网络输入
     → 1 通道，值 0..255，复制成 3 通道喂 ImageNet 预训练骨干
```

灰度缓存留 1024×576 而不是直接缩到网络分辨率，是**为了先在高分辨率二值化保住 1~2 px 细线**，
再下采样。这条顺序错了，虚线会整段消失。

**二值化阈值是主导变量，不是模型。** 实测 th190 明显优于 th130（th130 是谷底）。

## 4. 模型

MobileNetV3-Small encoder + 轻量 FPN-lite decoder，约 1.27M 参数，输出 `1×3×H×W` logits。

损失：加权 CE + Dice（细线类像素占比极低，必须加权）。

最强权重：`lane_seg_binary_off1280only.pt` —— 仅官方帧 + 二值 th190 @1280×720，实测 **0.93**。

## 5. 部署形态：G640

板上最终用 **G640**（灰度 640×360），不是最强的 A768（二值 1280×768 那版）：

| 代号 | 输入 | 算力 | 官方留出 |
|---|---|---|---|
| A768 | 二值 1280×768 | 1.00× | 0.910 |
| **G640** | **灰度 640×360** | **0.44×** | **0.870** |

**⚠️ 2026-10-31 决定：二值通道整个删除，RK 端坚决不做二值化。** 原因是模式位是**锁存**
不是按次请求 —— 为了拿一帧二值图去翻 MODE 2，会让随后所有帧都变成二值，红绿灯/导航
分支跟着失明（V17_5 实测 13→18 轮延迟）。所以把二值模型换成了灰度模型，用 4 个百分点
精度换整条链路的正确性。

这条决策的代价与依据都要写在报告里，不能只写"改成了灰度"。

## 6. 解码（`lane_decision.py`）

不是逐像素阈值，而是：

```
① 帧先验：只在下部参考带 (BAND_TOP=0.20 ~ BAND_BOT=0.90) 统计
② 按列统计虚线/实线像素占比 → 自车中心左右各取最近一簇
③ 簇内虚线像素占多数 → 虚线，否则实线
④ 时序锁存（确认 N 后切换），避免逐帧抖动
```

实测三种解码器在**同一批掩码**上的对比：

| 解码器 | 准确率 |
|---|---|
| 板上逐行投票 `SIDE_DASH_RATIO=0.50` | 0.810 |
| 同上，阈值改 0.31 | 0.920 |
| `lane_decision.py` 几何解码 | **0.940** |

**病根是 0.50 这个单边偏置**：虚→实 17 个 vs 实→虚 1 个。特征 AUC 0.942 很好，
但 17% 的虚线方向落在 0.45~0.55 之间，越过 0.50 就变成"实线"。

### 两条被证伪的路（别再试）

1. **调 `LANE_ROW_TOP` 完全无效** —— 0.45→0.75 准确率纹丝不动，0.85 才崩。
2. **任何"找虚线断口"的结构性方法注定失败** —— 掩码里虚线的纵向连续率中位 1.000，
   实线也有 35% 带空洞。模型学的是颜色不是几何，间隙分析 AUC 0.337，比随机还差。

### 阈值该取多少（代价不对称）

| 错误 | 后果 | 严重度 |
|---|---|---|
| 虚 → 实 | 少一次变道机会 | 轻 |
| 实 → 虚 | **指挥车压实线，违章** | 重 |

所以 `LANE_SIDE_DASH_RATIO` 取 **0.35**（0.890，实→虚 1 个），不取分数最高的 0.31
（0.920，但实→虚翻倍到 2 个）。

## 7. 已知局限

1. **自选偏差**：0.94 是在调参用过的那 50 帧上测的，对外应报 **0.89~0.90**。
2. **样本量小**：n=100 个方向，95% 置信区间约 ±6 个点。
3. **输入域漂移**：训练域二值图白色占比中位 4.0%，板上实测 39.7%（天空整片曝白）。
   模型目前靠"被天空挡住的行就跳过"侥幸扛住，这是碰运气的鲁棒，不是训练时保证的。
4. **场景捷径**：官方帧遮挡实验显示 96.5% 的预测与路面无关，模型部分依赖场景构图。

## 9. G640 的来历（补充）

`G640` 不是重新训练的模型，是**同一个灰度权重换输入分辨率**得到的：

- 权重：`lane_seg_gray_off640gray.pt`（灰度 + 官方同域微调）
- 输入：640×360，`th=190`，`arch=full`
- 转换：`mean=[[0]] / std=[[1]]` 直通（归一化烘在 ONNX 图里）
- 校准：48 张红绿灰度图

实测「同一套解码器、同一批留出帧、只改输入分辨率」的曲线（`res_sweep.py`）：

| 分辨率 | 灰度模型 | 相对算量 |
|---|---|---|
| 512×288 | 0.880 | 1.0× |
| **640×360** | **0.870** | **1.6×** |
| 768×432 | — | 2.3× |
| 1024×576 | 0.770 | 4.0× |
| 1280×720 | 0.800 | 5.7× |

**灰度模型反而低分辨率最好**（与二值模型「越高越好」完全相反）——

> 说明灰度用的是**粗亮度结构**，不是细节纹理。降分辨率对灰度几乎无损，
> 所以 640×360 用 0.44× 的算力拿到了几乎满档的精度。这是 G640 能成立的根本原因。

复现：
```bash
python res_sweep.py --res 512x288,640x360,768x432,1024x576,1280x720
python viz_compare.py     # 同一批帧上三个解码器的判决对比可视化
```
